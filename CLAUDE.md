# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What Geode is

Geode is the everything-tool for an index exotic equity derivatives desk: risk, pricing, execution, and data visualization in one permanent, keyboard-driven shell, built in Rust on gpui (Zed's UI framework) + gpui-component. **Phase 1 (the shell) is complete**: the binary opens a working i3-style tiling shell — layered TOML config with provenance (`geode-core::config`), the action registry + keymap engine (contexts, chords, sequences, layered override/unbind), the pure tiling tree + global workspaces (`geode-shell::tiling`), gpui rendering with click-to-focus and a status bar, the command palette (`ctrl+k`) over all actions and themes with fuzzy-match highlighting, and gpui-component theming with 38 bundled themes (`assets/themes/`, config key `[theme] name` in the `app` doc — a theme's name carries its own light/dark, `Gruvbox Light` and `Gruvbox Dark` are two themes, and there is no separate mode: the `mod+shift+t` toggle, the settings dialog's Dark mode row and the `[theme] mode` key were all retired by user ruling 2026-09-12, a leftover `mode` key warns at load and is removed by the next theme pick). Phase 1c polish is also complete: config hot reload (mtime watcher, last-good semantics), session layout persistence (`session.toml`), directional bindings (`mod+h/j/k/l` focus, `ctrl+alt+arrows` move, `shift+arrows` resize, `shift+d`/`ctrl+shift+d` duplicate a tile beside/below itself, `mod+e` orientation toggle, `ctrl+w` close), tiles *added* by kind from the palette (`Blotter: Split`, `Blotter: Split Horizontal/Vertical`, … — retitled from the original "Add Blotter" wording by user ruling 2026-09-09) with `[tiles] add = horizontal|vertical|auto` deciding the default direction — governed by `docs/superpowers/specs/2026-09-08-geode-add-tile-design.md`, title-bar toolbar with an inert filter field, workspace sidebar with a settings modal (`ctrl+,`), which-key hints, and bundled fonts (Inter = UI face, JetBrains Mono = data face via `shell::fonts::MONO`). Multi-window is deliberately not built yet (spec §3.6).

**Phase 2 (DataService) is complete**, governed by `docs/superpowers/specs/2026-08-30-geode-phase-2-data-design.md`. Phase 2a built storage and ingest: sentinel-gated discovery, CSV → DuckDB load, the grain split (`Position`/`Instrument`/`Underlying`/`UnderlyingPair`, so `SUM` cannot double-count), per-file generations with a live/archive pair per `(dataset, grain)`, `(dataset, batch, book)` partitioning, retention, and the freshness catalog. Phase 2b built the query path: the restricted scope grammar and its compiler, views and derived dimensions, `Attribution`/`ScopeSemantics`, the grain-aware tree compiler (one statement per view, `GROUPING SETS` bounded to the expanded depth), cross-dataset joins, ENUM dictionary encoding, the query pool with cancellation and coalescing, as-of routing, `Snapshot`, and the `DataService` facade. The generation set as-of resolves against now lives in the `generations` table, maintained inside the publish and sweep transactions rather than scanned fresh from the archive per requery (Phase 4a follow-up). The §7.1 <50ms requery contract holds at 1M rows — numbers in `docs/perf.md`.

**Phase 3c is implemented and merged-ready**, governed by `docs/superpowers/specs/2026-09-03-geode-phase-3-blotter-design.md`. `geode-blotter` renders any view definition (spec §6) as a collapsible, keyboard-driven hierarchy — dataset rows folded into a tree by grouping, honest attribution markers on cells the compiler said not to sum — hosted through Phase 3b's module contract. `cargo run -p geode-app -- --demo [rows]` (default 100,000) boots the shell on generated data with no real source configured, using the compiled-in `examples/demo-config/` layer; the shared frame's grouping slots (`ctrl+1..9`) regroup a blotter tile live, and its per-tile command line (`/` to find, `:` for `sort`/`group`/`yank` and the rest of spec §4.3) is the keyboard surface every row-shaping action goes through. `docs/phase-3-prerequisites.md` records what Phase 3's prerequisites fixed and the three items deliberately not implemented as written. The throwaway data probe — `geode-shell::dataprobe`, `geode-app/src/probe.rs`, `mod+shift+d`, opt-in via `GEODE_PROBE_DIR` — is deleted: it existed only to exercise the §7.1 budget's painted-frame half before the blotter existed to do that job for real (benchmarks recorded in `docs/perf.md`, which also records the painted-frame numbers themselves, or their template if a display was not available to measure them). Spec §1.2's done state was first exercised on a display on 2026-09-06: the blotter paints, and the first requery readings (38 ms end to end, session medians 12 ms query + 4.6 ms paint) hold the §7.1 <50 ms contract — recorded in `docs/perf.md`'s "Phase 3: the painted frame" section, which also records why the `DataTable` swap trigger (spec §6.6) is still unmeasured: the perf overlay's frame histogram records render-to-render intervals, so during a held key it reads the OS key-repeat period (~100 ms on macOS defaults), not paint cost; measuring the 8 ms pure-UI budget needs a render-duration reading (gpui's own overlay via `perf::gpui_overlay`, or a second histogram in `geode-shell::perf`).

**Phase 3a is done:** `[sources]` is read (`sources.toml`, `SourceSpec::from_doc`), `DataService` owns a discovery scheduler and one ingest runner, and modules reach it through `DataHandle` (`geode_data::handle`).

**Phase 3b is done:** the shell now hosts module occupants through the hosting contract (`geode_shell::module`), with one shared `Frame` entity every tile observes, count prefixes in the keymap engine (`KeyContext::counts`), session `tiles` restored from layout, a per-tile command line (`/` and `:` in the `tile` context), slot numbering via `ctrl+0..9` (`ctrl+0` clears a slot), and `RequeryStats` displayed in the perf overlay.

**Phase 3c is done:** the blotter crate, `--demo`, and probe deletion above. Its Task 0, gating every other task in the plan, split `crates/geode-shell/src/shell/mod.rs` (which had grown past 11,000 lines, including a ~7,880-line embedded test module) by seam into `render`, `drag`, `input`, `palette_ctl`, `commandline_ctl`, `occupants`, `session_io`, `hot_reload`, and a `shell/tests/` directory (one file per seam), leaving `shell/mod.rs` itself at roughly 800 lines of struct definition, construction and the handful of methods no seam owns.

**Phase 4a is done**, governed by `docs/superpowers/specs/2026-09-06-geode-phase-4-frame-features-design.md`. Dimensions can now name the grain that carries them (`grain = "instrument"`) instead of only being a built-in key column, and a `categorical` flag on `ColumnSpec` decides ENUM interning, pickers and the text rewrite alike. Load-time rules for both, checked in `validate_dataset`: a bare `dimension` naming no grain and not a built-in key column is an error and is dropped; a carried dimension whose declaring grain's key no grain's dimension key ever contains — `grain = "underlying_pair"` is the one built-in case, since the pair grain's dimension key collapses to the instrument key — is uncarriable, an error, and dropped; `textual = true` on a column no grain can route as a dimension is an error and `textual` is cleared (the column itself is kept). The text filter now requeries on every keystroke, made affordable by rewriting a textual+categorical column's `ILIKE` into an `IN` over its ENUM dictionary rather than a row scan: the zero-match, depth-2 case at 1M rows — a trader's first keystroke — went from 63 ms to 20.6 ms, holding the §7.1 budget (numbers in `docs/perf.md`'s Phase 4a section). The toolbar's middle is now the scope bar: slot, one chip per dimension selection plus text/expr chips, the live text field, and the as-of marker, rebuilt only on `Frame::versions()` changing — `mod+/` focuses the text field, `mod+p` opens the dimension picker, `mod+t` opens the as-of selector, `mod+z`/`mod+shift+z` undo/redo the scope. The picker's values stage is keyed `tab` to toggle a value (not `space`, which types into the filter), `ctrl+a` ticks every value the filter currently shows, `ctrl+x` clears the selection — both reclaimed inside `GeodeModal` the same way `tab` already is. The as-of selector (`HH:MM`, `HH:MM:SS`, `YYYY-MM-DD[ HH:MM[:SS]]`, RFC 3339, or `live`, plus recent-generation presets) drives a window-wide warning stripe and a status-bar segment while historical; `:asof undo` / `frame::as_of_undo` swap back. Times are the trader's local clock throughout: `HH:MM`/`HH:MM:SS` resolve on today's LOCAL date (`parse_as_of`, `geode-core::query`), matching the presets, the preview, the scope bar and the status segment, which all already showed local time. `:filter <expr>` / `:filter text <words>` / `:filter clear` set a tile's own filter layer, shown as `filtered` in its header and serialised with the tile. Scope changes now push a bounded 32-deep undo stack (cleared redo on a real mutation; a no-op pushes nothing), with the text field coalescing a whole focus session's keystrokes into one entry. `scopes.toml` is read from every layer and named scopes are recalled from the palette (`:scope save/load <name>`). Every scope, grouping or as-of mutation opens a flip barrier so every following tile promotes its staged snapshot in the same observe pass — never a half-updated screen — releasing early once every awaiting tile has arrived or after a 250 ms deadline (five times the §7.1 requery budget). `toml`'s `preserve_order` feature is on for `geode-core` and, by feature unification, the whole workspace; a schema's column order is file order everywhere it is iterated. Two things a maintainer must know: `FrameVersions.flip` is deliberately excluded from `BlotterTile::follows_changed`'s comparison — it only tells a tile with an already-staged snapshot when it is safe to promote, and a tile that mistakenly compares it would requery on every flip; and `keymap.mod = "ctrl"` is refused with an error diagnostic at load and reload (falling back to the default alias) rather than documented as colliding with the shipped literal `ctrl+…` bindings — a user ruling superseding the plan's original "document the collision" approach (Task 4b).

**Phase 4b is done**, governed by the same spec's §4. Every `eprintln!` outside tests (26 sites) now emits through `tracing` (`crates/geode-core/src/log/mod.rs`), tagged with one of six targets (`geode::ingest`/`query`/`config`/`session`/`shell`/`theme`); `[log]` in the `app` doc sets levels by target suffix, and its `to_targets()` caps every third-party crate at `warn` regardless of `[log] default` — only `geode`'s own targets follow the configured level. `geode_core::log::Ring` (capacity 4,096, fed by `RingLayer`) is the one in-process log a diagnostics tile reads: `drain_since` allocates nothing beyond each matching record's own `message: String` clone (the ring's mutex is held only for that copy, never for formatting), walks backward from the newest record and stops the moment it reaches `since` rather than scanning the whole ring, and `Ring::oldest_seq()` lets a reader report records lost to a wrap. `geode_shell::diagnostics::Diagnostics` is a shell-owned entity beside `Frame` — `sources: BTreeMap<String, SourceState>` (`health: Option<Health>`; a configured-but-not-yet-reported source is uncounted in `summary()`, not shown as some default health), `datasets`, `config`/`data_diagnostics` as two separately-capped, separately-counted batches (a config reload and a data-layer error never erase each other's error count), `frame_hist: FrameHistogram`, and a fixed 32-entry `ActionTail` of FNV-1a hashes (`[u64; 32]`, not `ActionId`s — a hash into a fixed array is allocation-free where cloning a `String` id isn't). `summary() -> Rc<str>` is cached on `version`, so a status-bar read clones a refcount, not a string. The config section is seeded at startup by `ShellView::new` and thereafter by `apply_reload`, and both fold in the same four groups in the same order — `config.diagnostics`, the refused `keymap.mod` alias (error), the retired `[app] modules.default` key (warning), and `build_keymap`'s own diagnostics. The first two of those extras are recomputed from the config; the keymap diagnostics cannot be (they need the registry as it stood at startup) and so ride on `ShellServices::keymap_diagnostics`, which `main.rs` fills. `main.rs` only ever *logs* all three, so seeding from `config.diagnostics` alone left them out of the tile until some later reload. The status bar's diagnostics-summary click opens (or focuses) a `geode-diagnostics` tile through `ShellView::open_module(kind)` — a generic door that focuses an existing occupant of that kind (tree or dock) or adds one through `ShellView::add_tile`, which records a `TileId`-addressed `pending_tiles` request for `ensure_occupants` to consume (`diagnostics::open` was retired by user ruling 2026-09-09; the palette's `Diagnostics: Split` rows add one instead) — over five sections (`sources`/`data`/`config`/`log`/`perf`, `[`/`]` to cycle, `/` to filter), with `:level <target> <level>` and `:overlay` as its command-line surface. `Health` moved from `geode-data` to `geode-core` (`geode-data` now just re-exports it) so the entity can hold it without breaking the "shell and data never depend on each other" rule. Every panic in `geode-data`'s four background boundaries (an ingest file's load, its pop-time catalog recheck, a discovery poll, a query pool worker) runs under `geode_core::panic::contained`, which the panic hook checks via `is_contained()`: a contained panic just logs at `error` (the app keeps running — no crash file), and an ingest load panic marks the source `Health::Failed`, not `Degraded` as the spec's original wording had it — a panic is a failed load, and the last good generation stays live. An uncontained panic writes `crash-<YYYYMMDD-HHMMSS-mmm>.log` under the user data dir (`OpenOptions::create_new`, retried with a numeric suffix on a same-instant collision, pruned to the newest 10) with the panic message, the ring's tail and the action tail resolved back to ids through `ActionRegistry::hash_names()`, then defers to the previous hook. Three things a maintainer must know: `Diagnostics::watch()`/`request_catalog()` queue their side effect but never call `cx.notify()` themselves — the caller's own `cx.notify()` in the same update block is what lets the bridge's drain see the request, and skipping it leaves it queued unseen until some unrelated mutation happens to notify; the frame histogram is copied into `Diagnostics.frame_hist` only on the existing ~500 ms reload-poll tick and only while `Diagnostics.watchers() > 0`, so an open-but-unwatched tile costs nothing per frame; and the daily log file's date (`geode.YYYY-MM-DD.log`) rolls on the UTC date, not the trader's local one — Phase 4a's "times are the trader's local clock throughout" ruling governs every *displayed* time, not the log file's own name (the crash file's timestamp is UTC for the same reason).

**Phase 4b's final whole-branch review (2026-09-08) found four Majors, fixed before merge.** `IngestEvent::Published`/`Failed` now carry the source name (`WorkItem::source`) through to `DataEvent::Health.source`, which the service used to key by the *dataset* name instead — a source whose `[sources.<name>]` name differs from its `dataset` no longer creates a phantom `sources` entry while the real source reads "no report yet" forever. A degraded *publish* (Phase 4a's carried-dimension violation, say) now also reaches the entity as `DataEvent::Health` — the service used to destructure `IngestEvent::Published` with `..`, discarding `health` entirely. And `Diagnostics` gained `versions: DiagVersions { sources, data, config, log_levels, perf }`, one counter per section bumped only by the mutators that section's row builder reads, so the diagnostics tile rebuilds only the section it is currently showing — the entity's single combined `version()` (still there, unrelated, for `summary()`'s cache) used to make a perf-only tick (the ~500ms reload-poll copy of the frame histogram, which fires whenever any diagnostics tile is visible) rebuild whatever section happened to be open, including the config section's expensive per-leaf explainer walk. Eleven Minors also landed: worth knowing are that `CatalogSnapshot` now carries the `AsOf` it was resolved under, so the data section's resolved-generation marker is suppressed rather than momentarily wrong during an as-of change; that a fresh diagnostics tile's log section seeds `since` from the ring's current `latest_seq` rather than `0`, so it never claims records it never had; and that `ensure_occupants` now creates tiles in sorted `TileId` order rather than `HashSet` order, so a `pending_kind_for_new_tile` request lands on a deterministic tile when two go occupant-less in one render pass.

**A scoped re-review of that fix wave (2026-09-08, same day) found two more Majors, both since fixed.** MAJ-3's own fix (above) had reopened MAJ-2's latch through a seam the review missed: a degraded *publish* set the entity's health, but the scheduler's own (then scheduler-local) transition tracker knew nothing about publishes, so its next clean poll thought it had already said `Ok` and stayed silent — a source with one degraded publish read `degraded` for the rest of the session, exactly MAJ-2's failure mode, reachable through the path MAJ-3 opened. The first fix — one `HealthTracker` (`crates/geode-data/src/service.rs`) owned by `DataService::open` and shared (`Arc`) by both sinks, with a single last-value map — itself introduced a worse regression a SECOND scoped re-review found the same day (NEW-4): a routine, content-blind scheduler poll (`Ok` whenever nothing currently looks stuck or malformed on disk — `CandidateState::Unchanged` says nothing about whether that file's *load* degraded) could silently clear a real, unfixed `Degraded`/`Failed` a publish had set, within about one poll interval, with nothing actually corrected — false-clean, not stuck-forever. `HealthTracker` now keeps two lanes per source, `discovery` (scheduler-written, content-blind) and `load` (ingest-written, content-aware), and reports the WORSE of the two — a clean discovery poll can never override a load-set problem; only a genuinely clean republish (writing the `load` lane back to `Ok`) can. A **third** re-review the same day found two more (round 4, both fixed): the worse-of-two comparison used `Health`'s derived `Ord`, which falls through to comparing the `reason` STRING once the variants tie, so between two simultaneous `Degraded`s — a malformed sentinel from discovery and a carried-dimension violation from a publish, an ordinary pair — the alphabet decided which one a trader saw and the other was never reported at all (NEW-5); and the `load` lane was keyed by source, so batch `BK1` publishing cleanly cleared batch `BK0`'s `Degraded` while `BK0`'s degraded rows were still live and queryable (NEW-6). Comparison is now by an explicit `severity_rank` (`Failed` > `Degraded` > `PendingTooLong` > `Pending` > `Ok`), an equal rank is decided by whichever slot CHANGED most recently (an identical re-report keeps its stamp, so repeated clean polls cannot flap the decision), each slot carries its producer's own `detail` and `report_*` hands back the DECIDING slot's `(Health, String)` pair for the sink to forward verbatim (before, each sink forwarded its own detail alongside another lane's health — a stuck file's name replaced by a just-published batch's, or a `Degraded` with a clean poll's empty reason), and the `load` lane is keyed by BATCH, worst-across-batches, so only a batch's own next publish replaces its entry. Round 4's own adversarial pass added one more: deciding a transition and emitting it are now a single step under the tracker's lock (`report_discovery_and_emit`/`report_load_and_emit`; the plain `report_*` doors are test-only), because the scheduler thread and the ingest runner thread report independently and `note_health` is last-write-wins — with the lock released in between, two decisions could reach the entity in the opposite order to the one they were made in, latching the entity on the older value while the tracker believed the newer one had been reported. Round 5 added the other half of that: a transition is recorded as reported only once its `DataEvent::Health` was actually **delivered**, so a refused send (a momentarily full event channel) is offered again on the next report rather than silently counted as shown — and the ingest sink's commit keys on the health send alone, never on `delivered && …`, which also folds in whether the paired `Published` event landed. **Two things a maintainer must know, recorded in spec §4.4's "Known gaps, deferred":** (1) **fixed on the follow-up branch (2026-09-08):** an `EventSink` returning `false` now means only "this event was not delivered" — full or closed — and no producer stops on one; the ingest runner (all three sites), the scheduler, and the query pool worker (a fourth consumer the original note missed — with `query_workers = 1` one refusal used to leave the app with no worker at all) each log the refusal once and keep producing, and `make_sink` distinguishes `TrySendError::Full` from `Closed`, logging a genuinely gone receiver once per sink while a full channel is only counted; (2) **fixed on the follow-up branch (2026-09-08):** the load lane is no longer in-process only — `DataService::open` seeds it, before `Scheduler::spawn` so no poll can speak first, from the health `file_generations` persisted for the generations that are LIVE (`Catalog::live_health`: `resolve_generations`' own resolution, with the `archived_only` guard in the join, one entry per batch whose live generation is not `ok`, worst-across-books by `severity_rank`), reported through the same `report_load_and_emit` door and emit closure the ingest sink's `Published` arm uses, so a restart no longer forgets a still-live degraded generation. Three things a maintainer must not "tidy" there: `live_health` takes **no time bound**, because `AsOf::Live` has none either (`Era::live()` leaves `generations: None`) and a generation stamped ahead of the host clock is live and summed — an `Utc::now()` bound reports the previous generation's health, a false clean; the `gen_id desc` tie-break is load-bearing, because the backfill guard is strictly-older so a corrected republish TIES its predecessor's `source_time`; and the filter names the four unhealthy labels rather than excluding `'ok'`, because `Health::from_parts` maps an unrecognised label to `Ok` and would seed a spurious one. Health is persisted per DATASET and the tracker is keyed per SOURCE, so the seed reads by dataset and files it under every source configured for that dataset — two sources on one dataset both get it, a dataset with no configured source gets none: over-reporting, never false-clean. Separately, both `process::exit` paths in `main.rs` (the argument-parse error, the demo-emit failure) now `drop(_log_guard)` before exiting — `process::exit` runs no destructors, so MIN-8's `WorkerGuard` never flushed and those two lines could be missing from the daily log file entirely, even though `tracing::error!` had already sent them to the appender's channel.

**Adding tiles (2026-09-08)** — there is no split verb and no default module kind: every tile is added by kind through `ShellView::add_tile` (`shell/add_tile.rs`), which fills a focused placeholder in place, makes the root of an empty region, or splits in the resolved direction (`tileadd::AddDirection`, `auto` = the focused tile's longer side from the pure layout). Showing a dock focuses it, empty or not — the region invariant is now "a dock only while visible", and `Dock::focusable()` (visible AND non-empty) is only `fallback_region`'s and directional focus's rule. A restored `tiles` record whose kind the roster lacks paints the placeholder and rides through `unplaced_records` to the next flush. Test fixtures bind `ctrl+v`/`ctrl+h` to `tile::add_rec_*` in a test layer (`tests::TEST_ADD_KEYMAP`); the shipped keymap has no such chord. Governed by `docs/superpowers/specs/2026-09-08-geode-add-tile-design.md`.

**Phase 4c was redesigned and no longer builds a config editor.** Phase 4 §5's TOML editor tile (`EditorState` with `.language("toml")`, squiggles, `ctrl+s`) is superseded in full by `docs/superpowers/specs/2026-09-08-geode-phase-4c-config-dialogs-design.md`: four purpose-built config *modals* — Views and columns, Sources, Scopes, Groupings — plus a read-only schema inspector, all on one shared two-stage scaffold in `settings_view`/`keybindings_view`'s mould, with create/delete/revert, override marking and drift detection implemented once and thin per-domain adapters supplying what differs. Do not build the editor; do not turn on the `tree-sitter-toml` feature. Three things that spec turns on: every verb is a *row* rather than a chord, because a focused `Input` inside a `GeodeModal` leaves no key space (`listfilter::nav_command` and `dialog::init_reclaimed_keybindings` have spent it); every field carries a destination, so a dragged column width writes `view_presentation.toml` and never forks a desk view; and applying stays the mtime watcher's job, so a dialog cannot disagree with the file it wrote. Its first task introduces `config_write` and migrates all six existing persist paths (`theme`, `fontsize`, `vimfind`, `frame`'s two, `keymap_edit`) onto it, replacing three separate `write_atomic` implementations — do not consolidate those by hand before then.

**Phase 4c Part 1 is done**: the write door, the `SourceSpec::from_doc` move, `ViewPresentationSpec`, and the object dialog's browse and edit stages over `Domain::Views`. `geode_shell::config_write` (`write`, `edit`, plus the crate-private `open`/`doc_path`) is the one door a config write goes through — no module opens a config file itself. It replaced three separate `write_atomic` implementations (`theme.rs`, `keymap_edit.rs`, `session.rs`) and now backs six persist paths (`theme`, `fontsize`, `vimfind`, `frame`'s two, `keymap_edit`), plus the object dialog's own saves. `ViewPresentationSpec` and its user-layer `view_presentation.toml` (`order`, `hidden` on `ColumnPresentation`, `width`) are merged *over* a loaded `ViewSpec` — in `config::load::load_views`, after the named-object merge — rather than into it: that is why dragging a column's width, hiding it, or reordering it never forks a desk view into the user layer (only a change to the column *set* does, routed through `Destination::Doc`), and why the desk's later changes to that view still reach a trader who has personalised its presentation. `shell::objectdialog` is the two-stage browse/edit scaffold; `Domain::Views` is its only adapter so far — Groupings, Scopes, Sources and the read-only schema inspector are Part 2, along with drift detection (`overrides.toml`) and per-field diagnostics (`Diagnostic.path`).

**Phase 4c Part 2a is done**: reverse stepping, an error-diagnostic gate on every write, and two more `Domain` adapters (`Groupings`, `Scopes`), each a palette-only action with no default binding. `NormalCommand::ToggleBack` (`shift+space`, `dialogmode.rs`) steps a selected row's value backward — the vocabulary had a forward step (`Toggle`/`space`) and no way back; both `Choice` and `Number` consume it through `Draft::step_selected`. An error-severity diagnostic on the open draft now blocks the batch: `apply::blocking_diagnostic` is checked *inside* `apply::commit_edit` itself, not just by its caller, so every path into `commit_edit` — `commit_or_confirm`'s own early check is a UX nicety, not the safety property — is covered by the one gate; a `Severity::Warning` (a desk rename, say) never blocks, only `Severity::Error` does. `d`/`r` (delete/revert) join the very same batch a field edit does, through `apply::commit_removal`, which takes bare `(doc, object)` keys rather than the `ObjectEdit`-valued map `commit_edit` fills, so there is no parameter a future caller could use to smuggle a value past the missing gate; a removal is deliberately *not* run through `blocking_diagnostic` (the diagnostic it would be gated on is usually the very thing `d`/`r` exists to clear) and skips the write debounce entirely (`Duration::ZERO`, not `WRITE_DEBOUNCE`) since a confirmed removal is a single already-decided act with nothing to coalesce — so a delete or revert reaches memory and disk *sooner* than an ordinary field edit does, on the confirming keystroke rather than 250 ms behind it, never a queued afterthought. **`d`/`r` also arm from the browse list (2026-09-19, spec §21):** on the selected row (the key in normal mode, the bar's button in either), on every domain — the same gates, the same confirm row in the bar's place, the same `commit_removal` — so a trader deleting or reverting a source never has to open it first; the edit stage keeps both. The confirm therefore lives on `ObjectDialogState.confirm`, not `Draft` (`arm_confirm`/`armed_confirm`/`answer_confirm` are the doors, every stage transition clears it through `disarm`), and `render::target_object`/`target_row` (formerly `editing_row`) resolve what it is about — the open object in `Edit`/`Column`, the selected visible row in `Browse`. **The browse target is an index, so it is recorded by name when armed (`confirm_target`) and the answer is refused if it no longer matches** — a config reload between `d` and `enter` re-ranks the list, and without the check the prompt named one object and `enter` deleted another; the dialog's own doors cannot move it (the armed block claims every other key, and `on_row_clicked` is dropped while a question stands — do not let a click through there, since `enter_edit` clears the confirm). `browse_action_bar` paints `Delete`/`Revert` buttons beside `n` off `selected_row` over the rows `build` already derived (never a second `derive_rows` per frame), and `after_removal` keeps browse in browse with the filter applied rather than walking `leave_edit`, which clears the query — and both landings resolve the cursor against `landing_rows`, the pending-aware config, because `commit_removal` applies to memory from a spawned task and a clamp against `services.config` is a no-op that left a last-row delete one past the end. `Domain::Groupings` (`shell::objectdialog::groupings`) edits `groupings.toml`'s nine `ctrl+1`..`ctrl+9` slots; its object is a bare array (`3 = ["book", "lhu"]`), the first adapter whose `to_table` is not a `toml_edit::Table`, which is why `Domain::to_table`, `set_object`, `object_text` and `apply::object_value`/`run_writes` all carry a `toml_edit::Item` rather than assuming `Table`. The slot number is the object's own **identity** (the top-level key), not a field inside it, so `slot` is a display-only `FieldKind::Text` rather than the design sketch's editable `Number` — a standing ruling on this plan forbids renames under instant-apply (a per-keystroke rename would write a table per prefix while stepping past it, orphaning every slot in between), and moving a slot's own number is a rename by another name. `Domain::Scopes` (`shell::objectdialog::scopes`) is the thinnest adapter: two read-only `FieldKind::Text` fields (`Selects`, in the scope bar's own "column ∈ values" spelling, and `Text filter`), plus one real verb, `o`, that overwrites the saved scope with the frame's current one. `o` arms `Confirm::Overwrite { forks: bool }` from `render::arm_overwrite`, which decides `forks` at that moment (whether the object's winning layer is already `Layer::User`) so the confirm prompt can disclose a fork before it happens; the frame itself is read a keystroke later, in `run_confirmed`'s `Confirm::Overwrite` arm (`shell.frame.read(cx).scope().clone()`) — the only place this dialog touches a `Frame`. `Draft::is_dirty` (and so whether `o` actually queues a write) compares `source` — the real object — against `baseline_source`, never the two painted `Text` summaries, because a summary can collide (two different scopes can render the same "column ∈ values" line) without the underlying objects matching. Neither adapter builds the design sketch's editable `name` `Text` field at all — a design-review ruling (recorded in this crate's Part 2a Task 4 and Task 5 reports) holds that renaming an object is unbuilt everywhere under instant-apply, not half-built on these two domains alone — and Scopes also drops the design's own "Load into frame" action row, a second ruling from the same review: it would duplicate the existing `:scope load <name>` / palette `scope::<name>` actions while being the one button in either dialog that mutates frame state rather than config, with nothing to confirm. **The one thing a maintainer must not tidy away here** (the whole-branch review's Major, fixed before merge): an *empty* rendering means opposite things at the two destinations, and the types say so rather than a comment. `apply::object_value` takes the `Destination` and answers `ObjectWrite::{Set, Remove, Nothing}` — `Remove` only ever for `Destination::Presentation`, because `view_presentation.toml` is an overlay where absence IS "I have no personalisation of this object", while removing a key from a domain's **own** doc means *inherit the layer beneath*: collapsing an emptied object to an absence there silently restored the desk's copy, so unticking a grouping slot's last dimension put the desk's chain back while the edit stage kept painting an empty one and `ctrl+3` kept regrouping by it. The other half is that the state is not offered at all — `Draft::step_selected` returns `Step::Refused` for the untick that would empty a `Destination::Doc` list (the config model has no empty chain: `GroupingSlots::set` refuses one and `from_doc` warns "slot N is empty; ignored"), and `render::refuse_step` names the verb that really does what the trader meant (`r` restores the desk's copy, `d` deletes their own). That is why `toggle_selected` returns a three-way `Step` rather than a `bool`: an inert row and a refused step are different things to say to a trader.

**Phase 4c Part 2 refinement is done** (spec §18): the Groupings dialog always lists slots 1–9 (`Domain::roster`; `ObjectRow.layer` is `Option<Layer>`, `None` for an unfilled slot, and every destructive or forking decision reads it as such — `d` on an empty slot says "is empty — tick a dimension to fill it" rather than the generic no-layer refusal); `n` creates an object through a committed name (`Stage::Naming`, `check_object_name` in `geode-core` shared with `Frame::save_scope`, `apply::commit_create` — one `Doc` write at zero debounce, never through the whole-draft `edits_for` map), with the edit header's `new` badge keyed on `Draft::is_new` alone for the stage's whole life (not `editing_row(shell).is_none()`, which would flicker it off the instant the row derives one executor tick behind the write) and the browse list still ranking by the typed name while naming, deliberately, so a near-collision stays visible before `enter` refuses it. Views lists the dataset's other columns as a second list, not a flag: `FieldKind::OrderedList` is `{ items: Vec<ListItem>, available: Option<Vec<ListItem>> }` (superseding the `member`-flag shape this paragraph once described — see spec §18.7's amendment). `items` is the object's own ordered list — the only one that is ordered, written, counted or reorderable — and `ListItem` carries a `kind: Option<String>` naming the `[[columns]]` kind a promotion needs. `available` is `None` where ticking IS membership (Groupings has no catalogue at all) and `Some(vec)` — possibly empty — where a catalogue exists (Views' dataset columns not already on the view): `x`'s per-domain refusal keys on the block's *existence*, never its emptiness, because an empty-but-`Some` catalogue must still let `x` demote a column, the exact "`x` goes dead on a fully-membered list" defect an earlier, emptiness-keyed build shipped. `space` on an `Available` row moves it to the end of `items`; `x` on an `Item` row in a list with a catalogue moves it to the end of `available`; both are `Doc` writes and hiding stays `Presentation`. `EditRow`'s third variant, `Available { field, item }`, exists so every consumer's match states what an available row means rather than forgetting it by omission — the compiler refuses a match that skips it. **Groupings dialog shortcuts (2026-09-12, spec §18.8):** a bare `1`–`9` opens that slot's edit stage from the browse list or from another slot's edit stage (`NormalCommand::Digit`, never `0` or a modified digit; the open slot's own digit says "already editing"), and a slot's edit stage **opens in the chooser, in normal mode, like every other domain** (user ruling 2026-09-14, reversing the 2026-09-12 chain-field landing — `ObjectDialogState::enter_edit` has no domain arm; a digit jumps slot to slot with no `escape` first). `i` opens the chain field from the chooser, and `escape` walks field → chooser → browse: the shared `Input` in the filter row's place, seeded with the slot's chain in the `book / lhu` spelling, where `/` and whitespace both separate, the row list below is the completion list for the segment being typed (`groupings::chain_candidates`, minus names already typed), `tab` completes the highlighted row, `enter` applies the typed names as the chain in typed order through the same `revalidate` + `commit_or_confirm` path a tick uses (a desk slot is forked and told so, no confirm since 2026-09-14), and `escape` cancels. Three things a maintainer must know: `enter_edit_stage` derives the draft from `apply::config_with_pending` (the live documents with the pending batch folded in), never from `services.config` alone, because inside the 250 ms write debounce the latter is the object as it stood *before* the last tick and a draft built from it both hides that tick and, outliving the flush, writes the object without it on its next tick (the review's Major, reachable in two bare digits: tick, jump away, jump back); `Draft::chain_entry` is a flag beside `confirm`, not a `Stage`, because the escape ladder and the browse cursor restore key on `Stage::Edit`; and the chain text IS `Draft::query` with the mode at `Filter` — that is what gives the field the keys through `sync_dialog_text` and mirrors keystrokes back with no second buffer — so `handle_chain_key` must stay dispatched ahead of the filter-mode branch, whose `enter` is a notice and whose `tab` is a drop. **The dialog's vocabulary is `groupable_columns`, not `pickable_columns` (2026-09-12, spec §8.2 amendment):** the query compiler groups by any column some *declared* grain carries as a dimension (`carries_all`) — key columns like `position_ref`/`instrument_ref` and carried dimensions whether or not they are categorical (a numeric strike) — plus derived dimensions, and the Groupings list offers exactly that set in schema order; the `mod+p` picker keeps its categorical-only list because it browses an ENUM dictionary, and it offers categorical *attributes* no grain can group by, so neither list is a subset of the other. A dataset declaring no grain (no measure or attribute) contributes nothing, so a test fixture for this dialog needs one measure. The same change gated a dimension's categorical *default* on `type = "utf8"` (`schema/mod.rs`): an `f64` dimension used to be sent for ENUM interning with no diagnostic.

**Market-data documents Part 1 (2026-09-12)** — `datasets.toml` has a second family: `family = "document"` with `key = [...]`, `axes = [...]`, `role = "axis"` / `"value"` columns and grainless `role = "attribute"` columns that are document-level (`ColumnRole::Attribute { grain: None }`). The two families are refused on each other's vocabulary per column (`validate_dataset` dispatches to `validate_document` and extends its diagnostics onto the shared reserved-column check, which applies to both), a document dataset has no grain, and `DatasetSpec::document_columns()` is the one column order storage and the document request share. A document dataset's `Dimension` columns must all be listed in its `key`; an unkeyed one is an error at load and the column is dropped (a per-row dimension within a document is an axis, and an unkeyed dimension would be groupable but unstored) — so `groupable_columns` on a document dataset is its dimensions alone, never an axis. `store::ddl::TablePair` replaced the `Grain` parameter of `publish_file`, `retention::sweep` and `apply_schema`: a measure dataset has one pair per grain, a document dataset exactly one (`{dataset}_document_live/_archive`), whose DDL (`create_document_table_sql`) emits `document_columns()` followed by `batch`, `book`, `source_file_id`, `gen_id`, `source_time` — `book` is always NULL for a document, but the column exists because every partition-keyed store statement joins on it. `store::document::publish_document` stages `geode_core::document::DocumentRows` (struct-of-arrays, in `geode-core` because `geode-data` dev-depends on the demo generator) through DuckDB's appender (`appender_params_from_iter`, an explicit `flush()` so a refused row can't ship as a silently shorter document, `Value::Date32` for dates) over one `Cell` plan built from `document_columns()` so staging and table order agree structurally, then runs the same publish transaction with the joined key (`geode_core::document::KEY_SEPARATOR`, `\u{1f}`) as the batch and no book, so generations, the backfill guard, as-of, retention and the catalog carry over untouched; `file_generations.path` is the synthetic `document://{source}/{dataset}/{batch}`, `mtime` is the receive time and `size` the message's bytes, since a document has no file to `stat`. `DocumentRows::validate` refuses a zero-row document ("document has no rows"): an empty live generation would read as "no document has ever arrived" rather than "the feed sent an empty one", and its generation would be recorded in the summary table while held by no rows at all — `StoreError::Document(String)` wraps this and every other validation failure, checked before anything is written. `Request::Document(DocumentParams)` compiles a plain select in axis order (`query::document::compile_document`) and is delivered as an ordinary `DataEvent::Query`; a document value's attribution is `DeterminedNonAdditive`. Its as-of arm pins the document's OWN resolved generation — `resolve_generations` filtered to this request's batch, `gen_id = N` against `live union all archive` — and reports `resolved_as_of` as that document's `source_time`; no generation at `t` compiles to `and false` (an empty snapshot, not an error), never affecting or reporting freshness for any other document the dataset holds. The live arm's `Freshness.as_of` is `Catalog::live_source_time(dataset, batch, None)` scoped to this one document, never the dataset-wide `dataset_as_of` fold, which would collapse every bookless key into one group. `DataService::as_of_bounds` now names tables through `ddl::history_of`, and the catalog's `live_rows`/`archive_rows` sum over `ddl::table_pairs` rather than `ds.grains()`, so a document dataset gets an as-of bound and a row count like any other — a count summed over grains read `0` beside a real list of live partitions. `ScopeSemantics::NotApplicable` and `Scope::applicable_to` exist for a scope selection on a dimension a dataset lacks (§3.4); the blotter's marker match treats it exactly like `SemiJoined` (`geode-blotter::core::plan`); **no query produces `NotApplicable` yet** — `compile_distinct`'s document arm calls `applicable_to` and discards the dropped names, because `DistinctOutcome` carries `(value, count)` rows and nothing else (no provenance field, no per-column semantics), so reporting the marker waits for Part 2's panel. The picker's values DO include a document dataset's dimensions (`query::distinct::document_select`): one union branch over the document pair, live reading the live table and as-of reading both sides under `generation_predicate(&resolve_generations(…))` resolved **dataset-wide** (distinct spans every key by definition, unlike `compile_document`, which narrows to one batch), offering only `Dimension` columns and never an axis. Its scope is the WHOLE scope, lowered grain-free (Part 2 Task 1 closed the item Part 1 parked here): the dimension selections `applicable_to` keeps through `scope_sql::selection_clause`, the text filter through `scope_sql::text_column_term` (extracted from `compile_scope_cached`'s own text block, so the dictionary `IN` for a categorical column and the row-scanning `ILIKE` for everything else are spelled once for both paths), and the expression filter through `scope_sql::render_expr`, one top-level `and` conjunct at a time. `compile_scope` is still the only place a *grain* routes any of them (`route`, `evaluable_at`, `membership`, `Era::relation`), but routing only ever decides *where* a term is evaluated and a document dataset is one table, so every one of those steps is a no-op there. Two rules carry over because the direction of the error matters more than the rule: a text filter with no surviving term — every dictionary dropped the needle, or the dataset declares no textual column at all — compiles to a literal `false`, because a needle over a dataset that cannot be searched matches nothing, never everything; and a selection or expression conjunct naming a column the dataset has no storage for is dropped, neither compiled (a binder error would fail the whole picker query on the one dataset with no `book`) nor collapsed to `false` (which would claim the document holds no such rows rather than that the question never reaches it) — the widening that leaves is the disclosed one `ScopeSemantics::NotApplicable` exists to report once the panel produces it. Three more things a maintainer must know. `geode_core::document::Column`/`Value` cover **f64, i64, utf8 and date only**, so `validate_document` refuses `timestamp` and `bool` on an axis or an attribute (error at `{ds}.columns.{name}.type`, column dropped — an axis dropped this way takes the dataset with it, since `axes` then names an undeclared column; a *value* is already held to the stricter f64/i64 rule and is not reported twice) and requires every key column to be `utf8` (error at `{ds}.key`, dataset dropped: the key is joined into the `batch VARCHAR` column and bound back as text, so any other declared type compiles and selects nothing) — widen the refusal only when Part 2 widens `Column`/`Value`. And a column named `book` is refused outright on this family (error at `{ds}.columns.book`, dataset dropped): `create_document_table_sql` appends its own `"book" VARCHAR`, so the DDL would carry the name twice and fail inside `DataService::open`, taking every other dataset with it — `RESERVED_COLUMNS` cannot carry that rule, since `book` is a legal grain key column on the measure side, which is why its doc comment now says its list is not the whole reserved set here. `compile_document` does **not** cast the key column to its ENUM type the way the view compiler casts a dimension (`refresh_enum` does maintain the type — `publish_document` refreshes it), so a document request returns the key as plain `VARCHAR`: a Part 2 measurement item, not a correctness one, since a document is one key's worth of rows rather than a million. Parts 2–4 (adapter tier, the panel, egress) are governed by `docs/superpowers/specs/2026-09-12-geode-market-data-documents-design.md`. **CVI slice values (2026-09-17, spec §6.3):** a CVI document carries three per-slice values — `forward`/`atm`/`skew`, one per `<slice>` — stored in the long form exactly as `param` is (repeated on every node row of the slice, "constant within a slice", so no document-family or storage change carries them; `cvi_params` declares them as `role = "value"` columns after `param`, and the demo database had to be deleted for it), refused by the kind when a slice lacks one or repeats one and on write when a slice's rows disagree (the writer reads the slice's first row), painted by the panel as the FIRST grid columns ahead of the ladder with their own formats (`PanelSpec.slice_values`, `MatrixModel.slice_columns`; a slice column arrives `DeterminedNonAdditive` exactly as `param` does, and it is `matrix::value_columns`' `spec.slice_value(..).is_none()` filter — not `PanelSpec::names`, which only `key_of` consults — that keeps the pivot from refusing the document as one with four value columns, so that filter is load-bearing, not redundant; a slice label colliding with an axis label is refused, since `Draft` indexes columns by label), refused by the pivot when a slice disagrees, skipped by a row bump (a column bump on `fwd` moves every term's forward), and rebased by `(term, label)` like any cell; a document without a spec-named slice column paints the ladder alone. The wire tag names are an assumption until the desk's XSD arrives — one `SLICE_VALUES` table in `crates/geode-documents/src/cvi.rs` is the only place to change them.

**Market-data documents Part 2 (2026-09-13)** is done: the adapter tier, the coalescer, the subscribed-source pipeline and the demo bus, governed by the same spec's §5–§6 and its new §5.6 "As built (Part 2)". `geode_data::adapter` is the trait tier a real broker adapter (Solace, not built here — the traits are its whole contract) will one day implement: `Adapter`/`Subscription`/`Egress`/`MessageSink`/`HealthSink`/`ConnectionState`, an `AdapterRegistry`, and `ChannelAdapter` — an in-process bus with no socket, doubling as both the crate's own test fixture and `--demo`'s producer. `ChannelAdapter` holds its inbound sender only weakly, so the bus closes for good once every `ChannelFeed` and outstanding egress is dropped: `subscribe` on a closed bus is `Err` rather than a `Connected` that then delivers nothing, and `egress()` answers `None` once every feed is gone — a capability held once can be lost at runtime, and both doors say so. `ChannelFeed::refused()` counts inbound publishes the bus itself could not queue; `SubscriptionWorker::refused()` (`geode_data::ingest::subscribe`) exposes a subscribed source's own dropped-message count the same way — neither has an in-app reader yet. **The worker holds the shared COUNTER (`MessageSink::refused_counter`), never a `MessageSink` clone**, and must not be "tidied" back: a sink is a sender, so one alive on that side means `unsubscribe` disconnects nothing, the receiver loop's `Disconnected` arm is unreachable on shutdown, and every join waits out a `MAX_WAIT` tick (250 ms) on the stop flag instead — serially per source in `DataService::shutdown`. A subscribed source is also *described* as one now: `SourceSpec::from_doc` clears the `paths` it warns are ignored (a reader must not store what it says it ignores), `geode_shell::diagnostics::SourceSummary` carries `adapter` and `topics` (empty for a directory source, which is how a reader tells the two apart), and the diagnostics tile's sources section paints `adapter:` + `topics:` for a subscribed source in place of the `path:` + `readiness` pair a directory source gets. `AdapterRegistry` and `DocumentRegistry` (`geode_data::documents`) both live on `DataServiceConfig`, filled by the app rather than `geode-data` itself: `geode_app::bridge::data_setup` always folds in `geode_documents::builtin_kinds()` (a document kind carries no state, so nothing a caller could sensibly leave out), while the adapter roster is the caller's own — `main.rs` registers a `ChannelAdapter` named `"demo_bus"` only under `--demo`; every other build passes `AdapterRegistry::default()` and reports every subscribed source as unservable, never a silent no-op. `geode-data` depends on neither `geode-documents` nor `geode-demo-data` — only `geode-app` sees a document kind at all, and `DocumentKind`/`check_kind_against` are the whole of what `geode-core` exposes across that seam. `SourceSpec` gained `adapter` (`CSV_DIR_ADAPTER` the default; anything else is `is_subscribed()`), `document`, `topics` (this plan's one grammar — `>` trailing levels, `*` one level, else literal, `/`-separated, the syntax the real Solace adapter will inherit), `coalesce` (`DEFAULT_COALESCE` 500ms; `"0"` opts into publishing every message) and `source_time` (`SourceTime::Receive` default, `SourceTime::Document(field)`), validated once at load: the named `source_time` field must be a document-level `Attribute` of type `date` or `utf8` (`sources.<name>.source_time`, `Error`, source skipped otherwise) — `source_time_of` (`geode_data::ingest::subscribe`) then reads a `Date` as that date's midnight UTC and a `Utf8` as RFC 3339 (which carries its own offset) per document, since the schema check is about the declared shape and this one is about what a given message actually sent. `Coalescer<T>` (`geode_data::ingest::coalesce`) is pure latest-wins-per-key with a minimum release spacing, every method taking `now` rather than a clock: a key's first offer within a window always releases at once, and every release restarts that key's own window from the release instant rather than the original offer, so a fast-repeating key cannot push its own next release out forever. The ingest runner (`geode_data::ingest::runner`) pops a queued `DocumentJob` ahead of any file, whatever the file's `Priority` — spec §5.4's own wording, that a document takes the `latest_other` rung, is amended here: a document publish is milliseconds and already coalesced to one per key upstream, so popping it first cannot starve a file load, and a single unconditional rule spares the runner a second priority vocabulary since a document carries no `Priority` at all; a queued document is dropped on `IngestHandle::shutdown` exactly as a queued file is, since neither queue drains before the runner thread returns. `ConnectionState` maps onto the discovery lane exactly (`DataService::open`'s `on_connection`): `Connected → Health::Ok`, `Reconnecting → Health::Pending` with the detail `"reconnecting"` beside it (`Pending` is a unit variant — the detail is a separate field, never an argument), `Lost { reason } → Health::Failed { reason }` verbatim. A parse, validate or `source_time_of` failure reports on the LOAD lane instead, keyed by batch when the bytes parsed far enough to yield one or by the raw topic when they did not — and a topic-keyed one is cleared by the receiver itself, because nothing else can: the lane's only other `Ok` writer is the ingest sink's `Published` arm, keyed by the document's own batch (`SPX.Z`, a different string from `marketdata/cvi/SPX.Z`), so the topic entry used to stand `Failed` for the rest of the session while the source published perfectly good documents. `Receiving::failed_topics` remembers the topics filed that way and reports `Health::Ok` under the topic on the first message from it that parses, validates and stamps (the tracker's transition dedupe keeps emits to real recoveries; a clean message on a never-failed topic costs one set lookup), which is why the closure the receiver is handed is a load-report sink (`LoadReportSink`, `(batch, Health, detail)`) rather than a parse-failure one. **Dataset-level column presentation is done**, governed by `docs/superpowers/specs/2026-09-13-geode-dataset-column-presentation-design.md` and reconciled there as §9. `dataset_presentation.toml` is a second personal overlay — **user layer only**, one `[<dataset>.columns.<col>]` table carrying the same seven presentation keys the view overlay does (`label`, `width`, `scale`, `precision`, `thousands`, `negative`, `colour`, same spellings and same parsers; `hidden` and `order` are refused with a warning naming `view_presentation.toml`, since membership and sequence belong to a view) — so "how this column looks" can live on the column rather than being said once per view and again in every view the desk adds later. **The resolution order is kind default → desk view column → trader's dataset-level → trader's view-level, per key**, and `geode_core::view::DatasetPresentationSpec::{from_doc, apply, owner_of}` is the whole reader: `owner_of` resolves which dataset owns a column (the view's own dataset first, then each join's in file order, first match wins — the order the compiler resolves names in), and `apply` merges each owned column's entry with the existing `merge_over`. **The maintainer trap is the merge POINT.** `config::load::load_views` calls `DatasetPresentationSpec::apply` *between* `ViewSpec::from_doc` (the desk view's own `[[columns]]` keys) and `ViewPresentationSpec::apply` (the trader's view overlay), and **below the loop that cross-checks each desk view's own `format.colour`** — that loop reads `view.presentation_of(..)`, so merging first blamed a dataset-level colour typo on `views.<v>.columns.<i>.format.colour` once per view carrying the column and hid a desk view's own bad colour behind a valid dataset-level one; a reader that applies the dataset overlay **after** the view overlay silently flips who wins — the trader's per-view divergence stops working, with no diagnostic and every test that only sets one layer still green. The doc is `atomic_depth` **1** (not the spec's original 3): one entry per dataset name, exactly as `view_presentation` is one per view, because the writer renders the whole `[<dataset>]` object. Its `colour` names are cross-checked against `colours.toml` **unconditionally** in `load_views`, never nested inside the `view_presentation` block — the first cut was, so with no `view_presentation.toml` (the default) an unknown colour was never warned about. `hot_reload`'s `views_changed` predicate gained `|| changed("dataset_presentation")`; the bridge needed nothing, `data_setup` already extending its diagnostics with `load_views`'s. **One column stage, two doors.** `Domain::writable(self, stage: &Stage)` is now stage-aware at all ten gate sites, and the read-only Schema inspector is writable in `Stage::Column { .. }` **alone** — `enter` or a click on one of its column rows opens the same seven-field stage the Views dialog's member rows open, writing `Destination::DatasetPresentation`. `ColumnDoor::{View, Dataset}` on `Draft.column_ctx: Option<ColumnContext>` is what tells the two apart: the Views door folds into the view's own list item over a desk+dataset baseline, the Schema door folds into `ColumnContext.item` over the unset presentation (its writer then emits only keys off the kind default) and renders the dataset's other personalised columns verbatim from `ColumnContext.overlay_object` (which is why that door must seed from `apply::config_with_pending`, never `services.config` alone — inside the 250 ms debounce the latter would render them as they stood before the last keystroke and undo it). `render::column_stage_target` is the one answer to "does this row open a column stage, and for which column", read by `commit_selected_row` (`enter`, in either mode) **and** `on_edit_row_clicked` — so a member-row click opens the stage and leaves filter mode exactly as `enter` does, closing 2c §9.9's standing minor; there is one rule about which rows are doors, not two. `objectdialog/dataset_columns.rs` is the Schema door's adapter (`overlay_object`, `item_for`, `table`, `row_summary`, `kind_for_type`, `provenance_of`, `ProvenanceInputs`); its `table()` normalises `[<dataset>]` to `columns` alone (a sibling key is already refused by the reader, so nothing there is state), and `kind_for_type` is why a `key` or `attribute` column — which `views::schema_role_kind` answers `None` for, and `views::kind_default` would therefore treat as a measure — opens with `ColumnFormat::TEXT` when its TYPE is `Utf8`/`Date`/`Timestamp`/`Bool`: without it, opening a `utf8` key painted precision 2, thousands on and a `sign` colour, and one `space` wrote a real key into the overlay. **Provenance is computed at paint, never stored.** There is no `Field.provenance`: `dataset_columns::provenance_of(&ProvenanceInputs, &Field)` answers `Provenance::{Desk, Dataset, View}` from `Draft::column_ctx` and `render::provenance_chip` paints it, so a just-stepped field reads `view` on the same frame rather than 250 ms later when the write lands (a stored value would go stale one keystroke after a step). `ProvenanceInputs` is built ONCE before the row loop — both its halves allocate, and seven clones a frame is per-frame heap churn. `ColumnLayers` holds **two** layers, `desk` and `dataset`: the chip reads `View` when, and only when, the field differs from the desk + dataset baseline, never from a captured view-overlay key — the writer omits every view key equal to the layer below, so such a key is unobservable and the next keystroke removes it, and a captured one made a field stepped *back* keep reading `view` until the stage was reopened (the final whole-branch review's named risk 4). **The Views stage's baseline is now desk + dataset.** `views::baseline_below(draft)` merges `Draft.dataset_layer` over `views::desk_baseline(draft)`, and both the fold and `views::presentation_table` read it, so **a view field set to the value the dataset level already gives writes nothing** — without that, every key the trader set at the dataset level would be copied into `view_presentation.toml` as a spurious per-view override, pinning that view against their own next dataset-level change. The layer travels on the draft because `Domain::to_table`, the writer's entry point and exactly where getting it wrong is silent, has no `Config` to read it from; `views::dataset_layer` resolves over **every column the view's datasets declare**, not only `view.columns`, because a column promoted out of the available catalogue is not in `view.columns` on the keystroke that writes it — and for the same reason `views::dataset_catalogue` seeds the available block's items from the dataset overlay too, so a promotion carries the dataset level and the stage, the writer and the member summary agree. `views::fold_into` names a key cleared by comparing against the **item's pre-fold value** — "this keystroke emptied it", not "the rendering is empty" — which is what keeps a cleared label's notice from being overwritten by a `width` nobody touched, and `Fold { key, to: Option<FellTo> }` gives the notice its three spellings: `<key> follows the desk again`, `... the dataset again` (the Views door, by which layer sets the key) and `... each view again` (the Schema door, where below the dataset level is the desk's key, which varies per view). Two smaller things worth knowing: millions is spelled **`"M"`**, never `"m"` (`views::scale_key`/`scale_keys`, and `ColumnPresentation::parse_format_keys` reads back exactly `none`/`k`/`M` — a lowercase `m` parses to no scale at all, silently); and `apply::blocking_diagnostic` gates a Schema column-stage write on the **datasets doc's own** diagnostics for that dataset, so an error-severity schema defect refuses every dataset-level edit on it with a notice about something the inspector cannot fix — known, as specified, and narrowing the gate per destination would reopen the no-carry-forward property it exists for. Display checks are pending on a real window, as §18.6's, §19.8's and 2c §9.11's are. **The Schema dialog is no longer labelled read-only (user ruling 2026-09-13):** its palette title is `Edit schema` (`Schema` for a day; the other five config dialogs all read `Edit …`), `READ_ONLY_NOTICE` names the door (`open a column (enter) to set how it paints`), and every footer names `enter` where it opens something — the browse list in both modes (`open`), the Views and Schema edit stages (`open column`) — and only while the SELECTED row opens one (`column_stage_target`, the same test `commit_selected_row` makes), so Views' `dataset` row, a Schema derived row and a column stage show no chip; it carries the `objectdialog-hint-enter` selector.

**Palette ranking (2026-09-12):** a palette row's match text is `"{title} {category}"` — the `searchable_text` shape the keybindings and settings dialogs already filtered over, with `split_label_indices` moved into `palette.rs`'s pure core so all three share one splitter — and every score earned at or past the title's end (a character's own base and the run bonus for continuing onto it) is divided by `CATEGORY_DIVISOR` (2), so the category is searchable but the lower-preference field: `work` mid-word in a title ("Framework tools", 31) outranks `work` at a word start in a category ("Workspace", 23), and the alignment — hence the highlight — lands on the title copy when both hold the letters. On top of the match score each row adds a usage bonus: `geode_shell::palette_usage::PaletteUsage` (pure, no clock — every method takes `now` in unix seconds) keys `action:{id}` / `theme:{name}` / `scope:{name}` (`PaletteItem::usage_key`) to a count and a last-used stamp, and `bonus` is a recency bucket (hour/day/week/older = 12/8/4/1) plus `min(count − 1, 6)`, capped at `MAX_BONUS` = 18 = two `RUN_BONUS`es. The ruling on where that cap meets the category discount (review 2026-09-12): a bare scattered match never beats a contiguous run whatever its usage; a maxed-out row whose only hit is in its category leads an unused title prefix on a query of three characters or fewer, ties it at four (registry order holds) and loses from five on — pinned by `a_used_category_hit_leads_a_short_title_prefix_and_loses_to_a_long_one`, the test to read before moving any of the three constants. `PaletteState::with_usage` bakes one bonus per row at palette open, so a keystroke's filter pass adds an integer per item and looks nothing up; an empty query therefore lists the rows a trader has chosen first (best bonus first, then registry order) with no separate "recent" section. Only palette dispatches count (`dispatch_palette_item`, every kind but `palette::toggle`'s own row) — a chord-dispatched action is not a palette use. The history persists as `session.toml`'s `[palette.usage]` table (`Restored::palette_usage`, `ShellServices::restored_palette_usage`), riding the layout's own coalesced ~500 ms flush through a `palette_usage_version` counter compared in `take_dirty_session_write` exactly like `last_frame_versions_written`, because the user config dir is mtime-watched for every `*.toml` but `session.toml` and a usage file of its own would trigger a config reload on every dispatch. The map is pruned to 256 entries by lowest bonus on record; a file with no `[palette]` table is an empty history and no warning.

**Dialogs now have two interaction modes**, governed by `docs/superpowers/specs/2026-09-08-geode-dialog-interaction-model-design.md`. A surface is modal iff it has verbs a user would reach for while *not* typing — normal mode owns the keyboard (letters are commands, `/` enters filter mode to type a query, `escape` walks a per-surface ladder outward), filter mode is the familiar always-focused-`Input` behaviour every dialog had before. Modal today: the keybinding dialog (`d` unbind, `r` reset — the capability filter-first could not express), Phase 4c's config dialogs, and — since 2026-09-12, spec §18, by user ruling — the settings dialog (`space`/`shift+space` step a value in normal mode, `tab`/`shift+tab` step in both, `enter` inert in both; `settings_view::route` is the whole key table as one pure function, `handle_key` only applies it, and the row click keeps its two-step select-then-step rule because this dialog's `enter` opens nothing). Filter-only, deliberately untouched: the command palette, the dimension picker, the as-of selector — none is dialog-shaped, and none has a verb that isn't "narrow the list" or "commit the highlighted row", so filter-first already serves them. `crates/geode-shell/src/dialogmode.rs` is the pure core (`DialogMode`, `EscapeStep`, `NormalCommand`, `escape_step`, `normal_command`) — no gpui, in the mould of `listfilter.rs` and `vimnav.rs`. **Stepping a value is five keys, not two (2026-09-13, spec §4's amendment):** `space`/`l`/`tab` forward and `shift+space`/`h`/`shift+tab` back, all claimed in `normal_command` so every modal surface — settings included, which needed no code of its own — gained them at once (`h` and `l` are no longer reachable as `Verb`, which was safe because no surface claimed either letter); the object dialog's FILTER mode steps on `tab`/`shift+tab` as well, through `render::step_selected_row` with §19.4's read-only gate on the way in, while `h`/`l` stay letters there and an open text field keeps `tab` for completing a chain segment. **And the edit footers are row-sensitive from the same ruling:** the change group and the `i` chip come from `Draft::selected_vocabulary` (the row under the cursor) rather than from the domain, so a `Choice` names the step keys and not `i`, an editable `Text` names `i` and not the step keys, a `Number` names both, a read-only `Text` or a list header names neither, a list row gets the forward key alone with the word that says which way it travels, the reorder group (`shift+j`/`shift+k`, and `x` where the domain offers it) is named only on a list item since that is the only row it moves, and the filter-mode footer names the change group shrunk to `tab`/`shift+tab` — the same reason an inert step names `tab`/`shift+tab` there and `space`/`shift+space` in normal mode, never the aliases — `Draft::offers_text_entry`, which asked the same question one level too wide and so taught `i` on Sources' `Dataset` row, is gone. Groupings' `i` is the one thing not row-derived (it opens the slot's whole chain, §18.8) and a one-option `Choice` is `Inert`, mirroring `step_selected`'s own guard. The mode pill (lowercase `normal`/`filter`, matching this crate's key-chip casing rather than the spec's shouted `NORMAL`/`FILTER`) lives in `dialog::mode_pill`; at the time this was written it could not join `render_modal`'s shared title row (fixed, shared across every dialog) and rendered as each modal dialog's own first content child instead — Phase 4c Part 2 refinement's `ShellModal.title_extra` slot (below) has since moved it into the title row for every modal dialog (settings included since it went modal). A 2026-09-11 amendment (spec §16) made this rigorous: the pure state (`mode`, `query`) is the truth, and `dialog::sync_dialog_text` is the *only* thing that moves focus or writes the shared `Input`, called at five seam classes — the key-path tail in `ShellView::handle_key_down`, the open door (`open_shell_dialog_with_key`), every row-click handler (a click never reaches the key path, so the handler is the transition's only tail), the object dialog's two confirm-button closures (`run_confirmed` is reachable by mouse), and every mouse handler that ends a dialog transition (the frozen-row click, a browse row's open, and the edit stage's tick click, row drop and chain-field completion click — see the "Dialog mouse parity" paragraph above); `press_verb` is the one audited mouse handler without a sync, because it can only arm a `Confirm` and moves neither mode nor query. A new transition site is therefore a pure mutation of `mode`/`query` and must never call `focus` or `set_value` itself — that is the sync's job alone. **The maintainer trap this closes:** `InputState::set_value` emits no `InputEvent::Change`, so a transition that wrote the field by hand had to clear it twice (once in the pure state, once in the `Input`) with no way for the compiler to catch a forgotten half; the sync's own text write is guarded by comparing against the `Input`'s current value first, both so an ordinary keystroke (already mirrored by the `Change` subscription) costs a compare and not a write, and so nothing but that one comparison ever has to remember `set_value` is silent. **The maintainer trap:** `dialog::init_reclaimed_keybindings` does not shrink under this model. Its `tab` binding suppresses gpui-component `Root`'s focus cycling regardless of what is currently focused, and filter mode still focuses the `Input`, so the `ctrl+a`/`ctrl+x` reclaims stay live too — what changed is only that new normal-mode verbs no longer need new reclaims of their own.

**A fork never asks (user ruling 2026-09-14):** an edit to a builtin- or desk-layer object in any config dialog copies it into the user layer on the keystroke, exactly as a user-owned object's edit applies, and the dialog's notice says so — `copied 'tree' to your config — r restores the desk copy` (`apply::fork_notice`; the shadowed layer is named from `shadow_of`, so a builtin object is not called the desk's). `Confirm::Fork` is gone: `render::commit_change` (formerly `commit_or_confirm`) reads `would_fork` *before* `commit_edit` moves the baseline — it is answered from the draft's pending writes, which the commit empties — and announces after a successful commit only, so a refused commit (an error diagnostic, a shell with nowhere to write) reports the refusal, since nothing was copied. The same ruling reaches Scopes' `o`: `render::overwrite_scope` writes at once on a desk- or builtin-owned scope (nothing is lost, `r` restores) with a notice naming both the replacement and the copy, and arms `Confirm::Overwrite` — now a unit variant — only on a user-owned scope, where the previous selection really is gone. The destructive confirms (`d`, `r`, and that `o`) are untouched. Harness: "a fork says nothing", "a fork asks first", "o asks before forking a desk-owned scope".

**Footer rows by category (user ruling 2026-09-14, interaction-model spec §19):** every modal dialog's footer — settings, keybindings, the object dialog's browse and edit stages — is a flat `Vec<Hint>` (`geode_shell::footer`, pure, `dialogmode`'s mould) rendered by the one `dialog::hint_rows`, which lays hints out as labelled rows in a fixed order: **move** (cursor and viewport), **edit** (anything that changes a value or object: stepping, reorder, `x`, `i`, `n`, rebind/unbind/reset), **go** (open, slot jump, `/`, `escape`, apply/cancel, a confirm's answer). A dialog decides which hints are live, never which row one sits on — that is the rule that keeps `space` on the same row on every surface. A hint's selector goes on its first chip AND every chip gets `"<selector>-<key>"`, which is how a test proves a particular key is taught (`settings-hint-change-tab`). The settings dialog's stepping group now reads exactly as the object dialog's.

**One answer per verb (2026-09-14, interaction-model spec §20):** `escape` discards what was being *typed* and never what was *stepped or ticked* — stated as a rule now. `vimnav::apply` is the one motion rule (a bare ±1 wraps, anything larger or counted clamps; `apply_clamped` for column axes and a blotter in visual mode), and the palette, picker and as-of selector all route through it with the full `listfilter::nav_command` set, the market-data tile with the same key set through its own fragment verbs (never `nav_command`). `dialog::ConfirmAnswer` + `dialog::confirm_row` are the one destructive question — the keybindings dialog's `d`/`r` arm it too (`KeybindingConfirm`) and have buttons. `dialog::value_chip` is the mouse form of `space`/`shift+space` on every steppable row (settings' second-click step is gone; the object dialog's `i`/`n` gained buttons). The picker's Values `escape` steps back to Columns (`back_to_columns`) and its row click selects while its tick toggles. A tile mouse-down while a `/` line holds text COMMITS it (`ShellView::leave_command_line`); `:` lines and `escape` still cancel. The diagnostics tile is deliberately untouched pending its rework.

**Cold start is on hold pending measurement — read `docs/ingest-cold-start-handoff.md` before touching it.** The 1.87× parallel-staging figure in `docs/perf.md` measures `read_csv` alone, not the real staging path (`read_csv` + `split_by_grain`), so it describes a narrower operation than the change would affect. That handoff also records what implementation hits — chiefly that `staging_raw` and `staging_{grain}` are fixed global names created with `create or replace table`, so concurrent staging would overwrite itself.

Key rules: Geode is a lens, not a brain (no financial computation in-app, only view-shaping); every action must be keyboard-reachable; nothing may stall the render thread; data-oriented design throughout (struct-of-arrays, allocation-free hot paths, per-frame heap churn is a defect).

## Architecture

Cargo workspace with strict layering, enforced by crate visibility:

```
geode-app          the binary: wires shell + modules + services together
  ├─ geode-shell   tiling WM, workspaces, palette, keymap engine, scope/as-of state, theming
  ├─ geode-blotter any view definition as a collapsible, keyboard-driven hierarchy (Phase 3)
  ├─ (modules)     future per-module crates: config editor, diagnostics…
  ├─ geode-data    DataService: sources, ingestion, DuckDB, archive, query API
  └─ geode-core    shared vocabulary: types, config model, ids, errors, perf utilities
geode-demo-data    deterministic seeded synthetic risk data (SoA) + the criterion bench harness
```

**Dependency rules:** `shell` and `data` never depend on each other, and never on modules; `geode-app` is the only crate where everything meets. No crate other than `geode-data` may open a file or socket — modules only ask DataService.

**Threading model (spec §2):** UI thread (gpui — renders, owns entity state, only ever reads prepared immutable snapshots) / query pool (DuckDB read connections, results delivered as immutable columnar snapshots over channels) / ingest (background writers publishing generation-stamped tables). Performance budgets in spec §7 are contracts: <8ms pure-UI actions, <50ms requery at 1M rows, ingest never drops a foreground frame.

**Testing strategy (spec §10.3):** test weight goes data layer ≫ shell logic ≫ modules. Shell logic (tiling tree, keymap resolution, config merging) is pure logic designed to be testable without a window; modules use gpui `TestAppContext`. TDD per house rules.

**A green suite proves less here than you would expect, and `scripts/mutation-check.sh` is the answer.** Five review rounds on the query path each found Critical, silent wrong-data defects, and the cause was the same every time: a fixture that could not reach the defect. The harness breaks one load-bearing behaviour at a time and runs the suite — a `SURVIVED` line is a branch no test can see. Run it after touching the compiler, scope lowering, as-of routing, publish, retention, discovery or the grain vocabulary, and **add an entry for every behaviour you change**. Its header documents the rules learned the hard way; the two worth knowing up front are that a test asserting on *markers* will not notice a wrong *value*, and that an entry can lie in four ways — no test behind it, two defences overlapping so neither is isolated, a mutation that breaks something other than what its name claims and is "caught" for the wrong reason, or an anchor that matches its file twice, so the FIRST match is mutated whichever site that is (`--anchors-only` reports stale and duplicated anchors in under a second and exits non-zero on any; run it before every merge — it found nine duplicates on 2026-09-09, one of which had been guarding the wrong site). An entry's optional 6th argument names the specific test expected to catch it, so day-to-day runs (especially `--changed`) check that one test before falling back to the full crate suite. **Commit before you mutate:** restoring a mutated file with `git checkout` discards uncommitted work with it.

## Workspace invariants and gotchas

- **Every gpui-kit and gpui-pre crate is `=`-pinned in the root `Cargo.toml`** — `gpui-component`, `gpui-kit-assets`, `gpui-base`, `gpui-component-macros`, `gpui-pre` (aliased `gpui`) and `gpui-pre-platform` (aliased `gpui_platform`), all from crates.io since 2026-09-18 (0.6.2 / 0.3.5; spec `docs/superpowers/specs/2026-09-17-geode-gpui-kit-upgrade-and-adoption-design.md` §2). gpui-kit depends on `gpui-pre` with a caret and gpui-component names its own siblings `gpui-base`/`gpui-component-macros` with a caret too, so an unpinned entry would let `cargo update` move gpui — or split the gpui-kit family — under us (it did, on the first build of this upgrade). Bump both families together, deliberately, on a branch; read the gpui-pre crate's description on crates.io for the zed rev it snapshots. There is no git dependency on zed or gpui-kit any more, so the old two-copies hazard the previous form of this rule guarded against cannot recur. The full explanation is in the comment in the root `Cargo.toml`. **Glossary:** wherever this file or a code comment says "the pinned rev", "the pinned release" or "the pinned gpui-component", it means these exact versions; the source a maintainer reads is the registry copy at `~/.cargo/registry/src/*/gpui-component-0.6.2/src/` (styled components), `gpui-base-0.6.2/src/` (unstyled behaviour) and `gpui-pre-0.3.5/src/` (gpui itself), and the sibling `gpui-pre-*-0.3.5` crates beside them for anything gpui itself re-exports, never a git checkout. `geode-shell` depends on `gpui-base` directly for one type, `CalendarView` (the as-of dialog resets the calendar to the day grid on open; gpui-component re-exports `CalendarState` but not the enum its `set_view` takes) — that is the only use of the unstyled layer outside `geode-app`'s pin, by user ruling 2026-09-19.
- **Every new lib/bin target needs `bench = false`** (and `[[bench]]` targets need `harness = false`) so `cargo bench` runs criterion cleanly instead of the built-in libtest harness. This is a workspace-wide invariant — copy the pattern from any existing crate.
- `gpui_platform` uses the `runtime_shaders` feature so Metal shaders compile at runtime without a full Xcode install (no-op off macOS).
- In `main`, `gpui_component::init(cx)` must run before any component use, and the root view is wrapped in `gpui_component::Root` (which also renders the dialog/notification layers).
- Dialogs open through `shell::dialog::open_shell_dialog`, never `window.open_dialog` directly — it's the one standard door that cancels pending keymap sequences and closes an open palette before setting `ShellView`'s own `modal` state. Modals are Geode's own instant, self-owned overlay (backdrop + panel painted directly in `ShellView::render`, palette-style — no animation), not gpui-component's `Dialog`: that component hardwires a 250ms entrance animation with no opt-out at the pinned rev, which read as slow next to the instant palette, so this crate stopped routing through it for its own modals.
- `geode_demo_data::write_csv` does no quoting/escaping — it relies on all string columns drawing from fixed comma-free vocabularies. Revisit if a vocabulary ever grows free-form values.
- Release and bench profiles keep debug symbols on purpose (profiling support, spec §7.4).
- **A tile occupant that tracks its own focus handle takes focus on any mouse-down, a drag grab included; every tile mouse-down path re-arms `pending_focus_restore` so the shell's chords survive — the two `on_mouse_down` listeners in `render.rs` and `try_arm_tile_drag` (`drag.rs`), which returns before the click-to-focus tail and so has to arm it itself. Keep all three.** The consumer has one exception (user ruling 2026-09-17): `render` clears the flag but **withholds the focus move only while the focused tile's occupant itself HOLDS the focused handle in insert mode** (`occupant_holds_insert_focus`, `occupants.rs` — `TileContent::holds_focus` answered by that occupant for the focused handle, which being its own input is never a shell surface, and `mode == insert`; the insert branch's own predicate, shared so the two cannot drift), which is what lets a module open an editor from a double-click without it going deaf a frame later; out of insert mode the restore runs exactly as before. Two different backstops sit under them, and they are not interchangeable. `render`'s `window.focused(cx).is_none()` net covers only a focused handle that was actually **dropped** — a focus-tracking tile *closed* while focused — because a dropped handle is the one thing that makes `Window::focused` report `None`. It cannot see a **workspace switch**: `ensure_occupants` retains occupants for tiles in every workspace, so a switched-away view is unmounted but alive, focus stays `Some`, and gpui silently falls back to `root_node_id` dispatch — which carries none of the shell's key listeners, so every chord dies. That case is caught in `ensure_occupants` itself, at the point where tiles leave the visible set: if any did and window focus is on a handle that is none of the shell's own (`focus_handle` plus the four `Entity<InputState>`s — see `holds_shell_focus`), the shell root takes focus immediately, not via the flag (which is consumed at the *top* of render and would be a frame late). Both conditions are deliberately narrow: anything broader would yank the caret out of a live focused `Input`. **The keyboard has the same rule (2026-09-14, Part 3's final review, I-3): every verb that moves which TILE has focus re-arms `pending_focus_restore` through `ShellView::note_keyboard_focus_move` (`occupants.rs`) when window focus is on a non-shell handle** — one door, called from `dispatch`'s `apply_workspace_action` branch (the four directions, the workspace switch, a dock show/toggle/move, a close) and from `open_module`'s focus-an-existing-tile arm; without it, `i` then `mod+l` moved the focused tile while the abandoned cell editor kept WINDOW focus, so every following bare key was dispatched by the matcher AND typed into that cell, count prefix and all. The editor is left open on purpose — it belongs to the module until commit or cancel, and `escape` on the tile once focus returns there still cancels it through the module's own fragment binding. (A keyboard focus move arms the flag with the OLD tile's editor focused; the 2026-09-17 exception on the consumer is withheld only while the focused tile's occupant itself HOLDS the focused handle in insert mode, and the newly focused tile holds nothing — even if its own abandoned editor still reports `mode == insert` — so the restore runs.)
- **Chords still dispatch from the scope bar's text field (2026-09-12).** `handle_key_down`'s filter-focused branch resolves any keystroke carrying ctrl, alt or cmd (`Modifiers::is_chord`; shift alone is typing) as a single keystroke through `single_keystroke_binding` against the `workspace` context alone, never `context_stack` — the focused tile's own bindings (a blotter's `ctrl+d`) must not fire behind a trader's typing — and reflects the frame's text back into the field afterwards, the one focused-field write outside the field's own typing. Bare keys and shift-only keys still go to the field untouched; the command line keeps only its palette-toggle exception; a modal owns the keyboard outright. **An overlay opened from the field returns focus to it on close** (same day's second ruling): `overlay_return_to_filter` is recorded by the palette's open arm and the dialog door and consumed by `return_focus_from_overlay`, the one door `close_modal` and `close_palette` both use. `close_palette` moves focus only when a palette was actually open — the dialog door calls it unconditionally, and an unconditional root focus there blurred the field a line before the door asked whether it held focus.
- **`DataTable` is never focused; its key context is bound to `NoAction` in `geode_blotter::init`, and a tile click re-arms the shell's focus restore.** Same door and reasoning as `geode_shell::shell::dialog::init_reclaimed_keybindings` — the table would otherwise swallow the vim-idiom keys the blotter's own bindings depend on.
- **A chevron click and a row double-click are `space` (2026-09-12): both go through `BlotterTile::expand_at_cursor`, the one path `zo`/`zc`/`za` also take.** The chevron listener in `BlotterDelegate::render_td` has no route to the tile but an event on the `TableState` it renders into, and `TableEvent` is gpui-component's closed enum, so the blotter emits its own `ChevronClicked` through a second `EventEmitter` impl on `TableState<BlotterDelegate>` (the orphan rule allows it: the event type is local). The listener stops propagation and ignores `click_count() > 1`, so a fast double-click on the chevron toggles exactly once rather than twice or three times — keep both halves.
- **A `NonAttributable` cell is NULL — read only through `f64_at`/`f64_value`; the blotter's cache is the one place a cell becomes text.** Reading a numeric column any other way (e.g. an `Array`'s own getter, which reads the underlying storage regardless of nullness) risks painting `0.00` for a cell the compiler explicitly declined to sum.
- **`FrameVersions.flip` is excluded from `BlotterTile::follows_changed` on purpose.** It only signals a tile with an already-staged snapshot that it is safe to promote (Phase 4a's flip barrier); a tile that adds it to `follows_changed`'s comparison requeries on every flip instead of just promoting.
- **`pending_tiles` is keyed by `TileId` and `unplaced_records` by the raw `u64` (the session's key type); both are retained to live tiles at the end of every `ensure_occupants`.** A request for a closed tile is dropped, never re-aimed.
- **Showing a dock exits fullscreen** (`Workspace::toggle_dock`): a fullscreen main tile plus a focused dock painted no focus ring and left `mod+f` dead; the show branch clears fullscreen first, the same way `move_to_dock` does.
- **`[ui] line_numbers` reaches modules as the `geode_shell::linenumbers::UiSettings` gpui global, and the keymap's bindings as `geode_shell::tips::Chords` — the workspace's two globals, both written only by the shell (startup and reload) and only read by modules.** The shell writes `UiSettings` (startup, the settings row, `ui::line_numbers_cycle`, hot reload) and the blotter observes it with `observe_global`; a module has no path to `ShellView`, and `ConfigReloaded` only fires for a `views`/`dimensions` reload, so neither existing route could carry a settings-row step to a live tile. Keep these the only globals unless the state is genuinely app-wide and module-visible. The blotter's gutter is painted inside the tree cell, not a column: `BlotterDelegate::column` widens the tree column by `gutter_px()`, and `on_ui_settings` must call `TableState::refresh` because the pinned gpui-component caches `column()`'s width in `col_groups`. Known, inherited trade-off: every keyed persist (`find_style`, `font_size`, `add` direction, `line_numbers`) spawns its write unordered, so two rapid steps can land the older value and the reload will re-derive it — a fix belongs in `config_write`, for all four at once.
- **Test fixtures bind `ctrl+v`/`ctrl+h` in a test layer** (`shell/tests/mod.rs::TEST_ADD_KEYMAP`) to `tile::add_rec_horizontal`/`_vertical`; the shipped keymap has no create-a-tile chord. `test_services()` carries a `rec` recording factory in its roster because an add on a focused placeholder fills it in place.
- **If you change `examples/demo-config/datasets.toml`'s columns — a column's `role`, `grain` or *order* included, not just the column set — delete the demo/probe database first.** `apply_schema` is `CREATE TABLE IF NOT EXISTS`, so an existing table is never migrated — a grown schema fails every publish with "table ... has N columns but N+1 values were supplied". A role change alone grows tables: making `strike` a carried dimension (2026-09-12) added it to every finer grain's table, where as an attribute it had lived in the instrument table only. A reorder is the quiet one: `publish_file` moves rows **positionally** (`insert into {live} select *, …` from staging, and the outgoing generation likewise `select *` into the archive) and both `create_table_sql` and `create_document_table_sql` emit their payload columns in TOML file order (`preserve_order` is on workspace-wide), so swapping two same-typed columns in `datasets.toml` against an existing database raises no error at all — it files each one's values under the other's name. `--demo`'s database lives at `$TMPDIR/geode-demo/<rows>-<seed>/geode.duckdb` (`geode-app::demo::demo_dir`, seed fixed at 42); delete that whole `<rows>-<seed>` directory, since the generated source CSVs under its `src/` are keyed to the same schema.
- **A module's insert mode is a tile-owned, focused `Input`; `ShellView::handle_key_down`'s insert branch is what lets it type at all** (`shell/input.rs`, after the filter-field branch, before the matcher): while a context on the stack carries `mode == insert` and window focus is on a handle the shell does not own, only single-keystroke bindings resolve (a chord against the whole stack, a bare key against only the insert-mode contexts) and everything else propagates to the input untouched. **A dropped `InputState` does NOT return focus by itself at the pinned gpui-component rev — `Root` holds a focused input strongly and only unregisters it from that input's own render, which a removed input never reaches.** An occupant must `window.blur(cx)` *then* drop the entity, in that order and both halves; skipping the blur leaves the handle alive, `Window::focused` never reports `None`, and the shell's own focus-return net (this file's `render`'s `is_none()` net, above) never fires — every chord dies for the rest of the session. `MarketDataTile::close_editor` and `geode_shell::module::recording`'s fixture are the two implementations; a third module doing text entry owes the same sequence.
- **A keymap fragment's predicate must be a plain conjunction — no `!`, `||` or `(` anywhere in it — or `keymap::fragments::check_fragment` drops the binding with an error diagnostic.** The check is textual (the predicate's first identifier), not a walk of the compiled boolean tree, so `blotter || workspace` and `(!blotter)` both pass a naive "starts with my context" test while actually binding in every context but the module's own tile — the widest possible shadow, from the one layer a trader cannot open to unbind it. Refusing every occurrence of the three tokens (not just a leading one) is what makes "a fragment can never shadow a shell binding or another module's" hold in fact rather than in the common case; do not loosen it to a leading-token check again.
- **`ModuleFactory::contexts()` is a separate answer from `kind()`** because a module's kind and the context its fragment binds can genuinely differ — the market-data panel factory is kind `cvi` (one roster entry per document kind) but returns `vec!["marketdata"]` from `contexts()` (one vocabulary shared by every document kind's panel); the default `vec![kind]` would silently drop every fragment binding for it, since `check_fragment` refuses one whose first identifier is not among the factory's own contexts.
- **The keybindings dialog reads a fragment binding as `Layer::Builtin`**, the same layer the shell's own shipped keymap reports: `r` (reset) removes a user override and lets the fragment show through again, and `d` (unbind) writes a user-layer `"none"` shadow over it rather than trying to remove a binding the trader's own config does not own — see `d_over_a_modules_fragment_binding_writes_a_user_layer_shadow` and `r_removes_a_user_override_and_the_modules_fragment_shows_through` in `crates/geode-shell/src/shell/tests/keybindings_dialog.rs`.

## gpui skills

The `gpui-kit` and `gpui-kit-design-guides` skills (available via the Skill tool) are vendored into this repo from longbridge/gpui-kit and tracked in `skills-lock.json` (they replaced the retired `gpui` and `gpui-component` skills on 2026-09-17, with the upgrade to the crates.io releases). Use them when touching any gpui rendering, entity, async, focus, or component code. **One translation to keep in mind:** the skills are written for the `gpui-kit` umbrella crate and spell paths as `gpui_kit::component::X` / `gpui_kit::base::X`; Geode does not depend on the umbrella (see the dependency comment in the root `Cargo.toml`), so those are `gpui_component::X` and, for the unstyled layer, a re-export or `gpui_base::X` here — the item names and signatures are the same, only the prefix differs.
